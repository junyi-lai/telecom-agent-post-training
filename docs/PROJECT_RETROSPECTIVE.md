# 项目复盘

本文只保留会影响实验设计、训练正确性、结果可信度或工程稳定性的经验。细节性操作手册和单 seed 中间报告已移出公开文档，但关键教训保留在这里。

## 1. 先把“失败”定义清楚

最初题目是宽泛的“失败驱动 Agent 后训练”。这个表述无法直接形成实验，因为“失败”可能指回复质量、工具错误或最终任务状态。最终选择 tau2-bench 电信域，是因为任务成功由数据库状态和确定性断言判定，失败也能拆成 max-step、非法工具调用、重复动作和状态不完整等可检查类型。

经验：先定义成功判据和失败分类，再谈数据策略。没有可重复的环境断言，失败感知采样只能停留在直觉层面。

## 2. 区分任务、轨迹、样本和 Prompt

项目数据中有多个容易混淆的层级：

- 官方注册表包含 2,285 个任务配置，但本次训练池是 164 个任务；
- 每任务运行 4 次得到 656 条基线轨迹；
- 388 条成功轨迹进入 SFT 候选池；
- 每次 SFT 实际选择的行数受 160K token 预算和覆盖约束；
- RL 普通组和失败感知组的 Prompt 行数分别是 164 和 328，但每个优化步的轨迹数仍固定为 64 条。

经验：报告任何比例前，必须明确分母是任务、episode、训练行还是 Prompt 行。把 656 条轨迹说成 656 个任务，或把 328 条 Prompt 说成两倍算量，都会造成错误结论。

## 3. 数据预算要控制重复

最初给每组设了 800K assistant-token 目标，但完整候选池只有约 314K token。若坚持这个目标，两组会几乎选中全部候选，实验干预消失。最终把预算降为每组 160K。

另一个问题是少数任务可能占满预算。为此引入每任务最多 2 条的上限；单纯加上限又会漏任务，所以先为 164 个任务各选择一条覆盖示范，再用剩余预算选择第二条。

覆盖后两组仍然可能过像，因为普通组和失败感知组会选到大量相同轨迹。最终失败感知组明确排除普通组第二遍的所有消息指纹，再按失败类型轮转。这样共享约 63% 覆盖核心，同时保留约 37% 的增量分配差异。

经验：比较数据策略时，要同时控制总 token、任务覆盖和重复轨迹；只控制其中一个，对照组可能实际上训练了几乎相同的数据。

## 4. 教师必须接受同一套环境校验

离线教师可以读取任务真值，因此生成成功示范通常比学生容易。如果直接把教师输出当作正确标签，可能引入教师自身错误。项目要求教师轨迹重新经过 tau2 严格评测，只有成功轨迹进入 SFT。

经验：教师是“示范生产者”，不是最终裁判。它和用户模拟器的角色必须隔离，教师不能参与在线 rollout。

## 5. 评测不能让另一个 LLM 决定结果

Agent 的输出“看起来合理”不等于任务完成。项目最终采用 tau2 的环境状态和任务断言作为严格成功标准。辅助过程奖励用于训练，但不替代最终判定。

经验：多轮工具任务应尽量使用可重复、可审计的成功函数。开放式 LLM 评分可以作为辅助诊断，但不能作为唯一实验结论。

## 6. AgentLoop 必须正确处理增量 observation

veRL 适配层逐轮接收完整 observation 历史。早期实现可能把历史重复追加，导致上下文膨胀、重复消息和错误 loss mask。修复后逐轮比较规范化消息，只追加新增后缀，并明确区分用户工具结果与策略已写入的助手消息。

经验：多轮训练框架中，数据接口的细微差异会直接影响梯度。上线正式训练前必须检查上下文长度、消息顺序、工具调用 ID 和 loss mask。

## 7. 并发不是越大越好

训练瓶颈曾看起来主要在 API 请求。实际调试后发现，Agent worker 的生命周期、每个 worker 同时持有的轨迹、以及环境 reset/step 的异步任务同样会积累系统内存。

稳定配置采用跨进程全局 DeepSeek 并发上限、确定性 worker 轮转、每个 worker 最多 2 条活跃 rollout，以及及时的环境关闭和内存回收。GPU 显存 OOM 与宿主机内存压力需要分开诊断；前者必须停止并报告，后者只能通过有记录的在途轨迹上限调整。

经验：并发配置要明确“每个进程”“每个 worker”和“全局”三个层级。把任务并发直接当成 API 并发，或无限增加在途 rollout，都可能把性能问题转成稳定性问题。

## 8. 主备路由要解决快速重试、总时限和熔断

长训练不能只靠一次请求成功。主通道遇到 429、5xx、连接错误或超时时，需要在有限次数内快速重试；重试等待和单次请求都必须受总截止时间约束。仍失败后才使用备用通道。备用通道遇到 401、402、403 或余额不足时应熔断，避免持续扣费或无效请求。

经验：日志应记录通道名、错误类型、重试、fallback 和延迟，不记录密钥。限流与熔断状态需要跨进程一致，不能误认为每个 Python/Ray 进程内的本地门就是全局并发。

## 9. 断点续跑不能重采样有效轨迹

评测期间模型部署别名可能变化，或少量轨迹因基础设施原因失败。恢复时必须先保留原快照与哈希，只补跑损坏或基础设施失败的记录；已经有效终止的轨迹不得重新采样。

经验：任务 ID、seed、模型 revision、原始 provenance 和规范化名称要分开保存。别名只能作为请求映射，不能静默改写历史结果。

## 10. 统计单位决定结论强度

同一任务的三个 seed 是相关重复测量，不能把 120 条轨迹当作 120 个独立样本。项目先计算每任务三 seed 平均成功率，再对相同任务 ID 做 10,000 次配对 bootstrap。

最终结果为：

| 比较 | 平均差 | 配对 95% 区间 |
| --- | ---: | ---: |
| uniform SFT − base | −25.00 个百分点 | [−37.50, −12.50] |
| failure-aware SFT − base | −4.17 个百分点 | [−13.33, +5.00] |
| uniform GRPO − base | −7.50 个百分点 | [−17.50, +2.50] |
| failure-aware GRPO − base | +8.33 个百分点 | [0.00, +17.50] |
| failure-aware GRPO − failure-aware SFT | +12.50 个百分点 | [+4.17, +21.67] |
| failure-aware GRPO − uniform GRPO | +15.83 个百分点 | [+6.67, +25.00] |

failure-aware GRPO 在本实验中最高，相对自身 SFT 起点和 uniform GRPO 的区间在零以上；相对 base 的区间下界触及零，因此不能说已经稳健证明优于 base。普通 SFT 的下降也提醒：后训练不保证提升，需要单独排查示范、采样和优化过程。

经验：报告观察值、任务级区间和统计单位；不要为了突出提升而忽略触及零的区间。

## 11. 执行差异必须进入结论边界

两组 GRPO 的资源恢复过程并不完全相同：普通组完成 75 步时使用了更早的在途批次上限；失败感知组恢复后使用更低的在途批次上限，并加入额外的 worker 调度与内存回收约束。两组仍保持相同任务、每步轨迹预算和 75 个优化步，但结果不能完全归因于数据策略。

经验：训练日志和运行元数据要保存有效 profile、配置 hash、数据 hash、checkpoint 和恢复点。比较算法前，应先检查两边实际生效的恢复配置。
